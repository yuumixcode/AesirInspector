# Odin Inspector 包化方案、程序集划分与风险清单

> 目标：把 `Assets/Plugins/Sirenix/` 下的 Odin Inspector 变成结构规范的 Unity Package（UPM），
> 且**可直接导入使用**。

---

## 1. 结论先行

**推荐方案：A（DLL 保真包）+ B（反编译源码包）双轨。**

| | 方案 A · DLL 保真包 | 方案 B · 源码包 |
|---|---|---|
| 内容 | 原厂 DLL + 资产载荷，按 UPM 重排 | 反编译 `.cs` + asmdef 重建 |
| 可用性 | ✅ **100% 可用**，零行为风险 | ⚠️ 需大量修补，且存在**架构级障碍** |
| 风险 | 极低 | 高 |
| 用途 | **生产使用** | **学习研究**（可作为方案 A 的并置参考） |

**只走方案 B 是走不通的**，原因见 §4。方案 A 已在本次分析中实际构建并校验通过（§2）。

### 2.2 为什么**不能**"整理"成 Runtime/ Editor/ 的样子

这是本方案最反直觉、也最容易踩坑的一点。三条硬约束：

1. **目录名被代码硬编码**
   `SirenixAssetPaths` 静态构造里直接拼接
   `OdinPath = SirenixPluginPath + "Odin Inspector/"`、
   `SirenixAssembliesPath = SirenixPluginPath + "Assemblies/"`。
   改名为 `Runtime/` 或 `Runtime/` → 路径解析失败，Odin 抛错并回退到 `Assets/Plugins/Sirenix/`。

2. **同名 DLL 靠目录共存**
   `Assemblies/Sirenix.Utilities.dll` 与 `Assemblies/NoEditor/Sirenix.Utilities.dll` 是
   **同名同命名空间但内容不同**的两份程序集，靠各自 `.meta` 里的 `PluginImporter` 平台设置区分。
   一旦合并目录或重命名文件，平台选择立刻失效。

3. **`.meta` 与 `package.json` 共存**
   UPM 包里 `.meta` 是**被 Unity 读取并生效的**（插件平台设置、GUID 全部保留），
   而 `package.json` 是 UPM 清单。两者可以共存，互不干扰。

### 2.3 必须保留 `.meta` 的理由

| 保留项 | 破坏后果 |
|---|---|
| `Sirenix.OdinInspector.Editor.dll.meta` 的 GUID | `OdinPathLookup.asset` 的 `m_Script` 悬空 → Odin 无法初始化 |
| 三个变体的 `.meta` 平台矩阵 | 播放器构建时报 `UnityEditor` 缺失 / AOT 平台 `Reflection.Emit` 缺失 |
| `OdinPathLookup.asset.meta` 的 GUID | 路径自举走"慢速全工程扫描"分支，工程加载变慢 |
| 着色器 / 图标图集 `.meta` | Odin 界面缺图、SDF 图标不可用 |

本次构建已做**逐字节校验**：`diff -q` 对比原厂与包内 `.meta`，全部一致。

### 2.4 安装方式（重要）

必须作为**嵌入式包**安装：

```bash
# 1. 先把原安装挪走，避免重复程序集
mv Assets/Plugins/Sirenix ~/Sirenix_backup

# 2. 放进工程 Packages/
cp -R com.sirenix.odin-inspector <工程>/Packages/
```

**为什么不能靠 `manifest.json` 的 `file:` 指向工程外目录？**
`SirenixAssetPaths` 会用 `DirectoryInfo(path).Exists` 校验推导出的目录。
只有物理位于 `<工程>/Packages/<pkg>/` 下、AssetDatabase 路径与磁盘路径一致时才为真。
若由 `Library/PackageCache/` 解析（git / registry 包），
AssetDatabase 报的 `Packages/com.sirenix.odin-inspector` 在磁盘上**不存在**，路径自举失败。

```
Sirenix.OdinInspector.Editor/Sirenix/OdinInspector/Editor/Drawers/…
Sirenix.Serialization/Sirenix/Serialization/Formatters/…
```

### 3.2 asmdef 划分设计

若强行做成 asmdef 源码包，映射关系只能是：

```
Runtime/
├── Sirenix.OdinInspector.Attributes.asmdef    ← 无平台约束（纯 runtime）
└── Sirenix.Serialization.Config.asmdef        ← 无平台约束

Editor/
├── Sirenix.Utilities.asmdef                   ← includePlatforms: ["Editor"]  ★被迫
├── Sirenix.Serialization.asmdef               ← includePlatforms: ["Editor"]  ★被迫
├── Sirenix.Reflection.Editor.asmdef           ← includePlatforms: ["Editor"]
├── Sirenix.Utilities.Editor.asmdef            ← includePlatforms: ["Editor"]
└── Sirenix.OdinInspector.Editor.asmdef        ← includePlatforms: ["Editor"]
```

**★ 两个被迫的 Editor 约束，正是方案 B 的致命伤**：

反编译只能还原**一个平台**的编译结果（Editor 版）。
而原厂是"一份源码 → 3 次条件编译"。`#if UNITY_EDITOR` 的**边界在 IL 中已完全消失**，
反编译产物是预处理**之后**的形态，无法自动反推回"一份带条件编译的源码"。

后果：
- 若打成 Editor-only asmdef → **播放器构建里彻底没有 `Sirenix.Utilities` / `Sirenix.Serialization`**，
  `[OdinSerialize]` 的运行时序列化在 Build 后失效（功能性回归）。
- 若想恢复 runtime 能力 → 必须人工在 2700 个类型里手工标定 `#if UNITY_EDITOR` 边界，**不具可行性**。

### 3.3 推荐的混合形态

```
com.sirenix.odin-inspector/
├── Assemblies/          ← 原厂 DLL（保证运行时功能与平台矩阵完整）
├── Odin Inspector/      ← 原厂资产载荷
└── Documentation~/
    └── Sources/         ← 反编译源码，仅作阅读参考
```

`Documentation~` 以 `~` 结尾，**UPM 与 Unity 都会忽略**，不会参与编译，
因此其中的 `.cs` 不会造成任何冲突，又能随时用 IDE 打开阅读。

## 4. 源码编译可行性实测（方案 B 的核心证据）

为了让"能不能重建"这个问题有**硬数据**而不是推测，搭建了编译验证台：
Roslyn `csc`（.NET SDK 8.0.424）+ Unity 参照程序集，按拓扑序重建 7 个程序集。

### 4.1 参照集能力矩阵（决定性发现）

Odin 源码同时需要三类互相**矛盾**的 API：

| 参照集 | `System.Index`<br>(netstandard2.1) | `System.Range` | `AppDomain.`<br>`DefineDynamicAssembly`<br>(netfx) |
|---|---|---|---|
| `NetStandard/ref/2.1.0` | ✅ | ✅ | ✅(2) |
| `NetStandard/compat/2.1.0/shims/netfx` | ❌ | ❌ | ❌ |
| System Mono `4.7.1-api` | ❌ | ❌ | ✅(24) |
| **`UnityReferenceAssemblies/unity-4.8-api`** | ✅ | ✅ | ✅(24) |

> **只有 `unity-4.8-api` 三者齐全** → Odin 的真实编译基准是
> **Unity 的 .NET Framework 4.8 API 档**，而不是工程当前设置的 .NET Standard 2.1
> （工程 `apiCompatibilityLevel: 6` = .NET Standard 2.1）。
>
> 这也解释了为什么 Odin 必须以 DLL 形式分发：
> 预编译 DLL 在 netstandard 工程里靠 Unity 的 `shims/netfx` 兼容垫片完成类型转发，
> 从而对用户的 API 兼容级别设置**免疫**。

### 4.2 迭代收敛过程

| 里程碑 | 关键变化 | 结果（通过 / 7） |
|---|---|---|
| 起点 | Mono 4.7.1-api + 原始 Unity 模块 | 1（仅 Attributes） |
| ① 换 netstandard2.1 参照 | 补上 `System.Index` / `System.Range` | 3 |
| ② 换精选 `unity-4.8-api` | 补上 `AppDomain.DefineDynamicAssembly` | 4 |

### 4.2.1 迭代途中踩到的两个"假错误"（值得记录）

这两类错误曾让人误判方向，实际与 Odin 源码无关：

1. **参照集目录整体引用 → 二义性伪错误**
   把 `unity-4.8-api/` 连同 `Facades/System.Runtime.dll` 一起引用，
   `System.Type` 会同时来自 `mscorlib` 与 `Facades/System.Runtime`，
   于是 `TypeExtensions.GetNiceName(System.Type)` 报"与自身二义"（一次 144 个）。
   → 只精选核心程序集 + **单独**补 `Facades/netstandard.dll` 一个门面。

2. **编译产物残留 → 自我引用伪错误**
   验证台把上一轮编译出的 `Sirenix.Utilities.dll` 当作引用又喂回去，
   导致同一类型出现两份定义，同样报"与自身二义"。
   → 每次运行必须清空 `bin/`，并显式排除"正在编译的程序集自身"。

### 4.3 五类根因与修法（修订版）

**根因 1 · 参照集错配** —— 可修，已定位
- 症状：`CS0518 预定义类型"System.Index"未定义`、`CS1061 AppDomain 未包含 DefineDynamicAssembly`
- 修法：精选 `unity-4.8-api` 核心程序集 + **单独**补 `Facades/netstandard.dll`

**根因 2 · Unity internal 类型访问** —— 可修，但需专门工具
- 症状：`Sirenix.Reflection.Editor` 报 13 个 `CS0122 "GUILayoutEntry"不可访问`
- 涉及的 internal 类型实测（`TypeAttributes = 0x100000 NotPublic`）：

  | 类型 | 所在模块 |
  |---|---|
  | `UnityEngine.GUILayoutEntry` / `GUILayoutGroup` / `ScrollViewState` | `UnityEngine.IMGUIModule` |
  | `UnityEngine.UIElements.Panel` | `UnityEngine.UIElementsModule` |
  | `UnityEditor.ContainerWindow` | `UnityEditor.*` |

- 原厂为什么能编译？实测排除两条路：
  - ❌ Unity 未开放访问：`UnityEditor.dll` **无任何 `InternalsVisibleTo`**；
    `UnityEngine.*Module.dll` 只对**其它 Unity 内部模块**开放
  - ❌ 原厂 DLL 里**没有** `IgnoresAccessChecksTo` 特性（`TypeRef` / `CustomAttr` 表均已核查）
  - ✅ 结论：Sirenix 用**公开化（publicized）的 Unity 参照程序集**编译
- 修法：本工作区已实现公开化工具（`tools/publicize/PublicizeUnity.cs`，
  基于 Unity 自带的 `Unity.Cecil.dll`），把 `Managed/UnityEngine/*.dll` 的
  internal 类型/字段/方法提升为 public，编译时**只引用公开化副本**
  （与原件同时引用会导致类型二义性）
- **关键细节**：公开化**不得提升 `virtual` / `abstract` 成员的可见性**。
  Unity 的 `GUILayoutEntry.ApplyStyleSettings` 是 `protected virtual`，
  Odin 以 `protected override` 覆写；一旦提升为 `public`，
  覆写方立刻撞 `CS0507 无法更改访问修饰符`。
  这属于**跨程序集重写契约**，必须在公开化时保留。
- 注：**Roslyn 实测不采纳 `IgnoresAccessChecksTo` 破障特性**
  （public / internal 定义、最小复现均报 CS0122），该捷径已排除。

**根因 3 · ILSpy 产物缺陷** —— 可修，逐案判断
| 子类 | 实例 | 修法 |
|---|---|---|
| 枚举字面量美化 | `MethodImplOptions.AggressiveOptimization`（实为 `512`，该成员在所有 Unity profile 中都不存在）<br>`FileAttributes.None`（实为 `0`，该成员不存在） | 换回字面量：`(MethodImplOptions)512`、`(FileAttributes)0` |
| 丢失类型限定 | `StackFrame`（`UnityEditor` vs `System.Diagnostics`）<br>`Clipboard`（`UnityEditor` vs `Sirenix.Utilities.Editor`）<br>`SceneView`、`ValidationResult` | 加 using 别名或显式限定 |
| 控制流改写失真 | `CS1939 无法作为 ref/out 传递范围变量`——原始 `for` 循环被改写成 LINQ，`ref t` 落在范围变量上 | 加语义等价的包装方法（`CanCreateInstanceSafe`） |

**根因 4 · 编译器生成类型泄漏** —— 需人工还原
`_003C_003Ec__DisplayClass2_0` 等闭包/匿名类型名泄漏，ILSpy 未能还原为 Lambda。

**根因 5 · 跨程序集同名类型残留** —— 需逐案限定
`ValidationResult`（Odin 的 vs Unity 侧同名）、`SceneView` 等，
编译器选中了错误的一侧，报 `CS1503 ref 无法转换`。

### 4.4 可行性判定

| 维度 | 结论 |
|---|---|
| 能否编译？ | **6/7 程序集零错误；最大的 Editor 程序集仅剩 15 个错误**（原始 5,970 个） |
| 修补量？ | 累计 5 条全局规则 + 1 条按文件规则，涉及 6 个文件、约 20 行 |
| 能否等价替代原厂 DLL？ | **不能** |

**为什么"能编译"却不等于"能替代"**：
原厂是「一份源码 → 按 3 类平台条件编译 3 次」（§3.2）。
反编译只能还原**其中一次**的编译结果，`#if UNITY_EDITOR` 的边界在 IL 中已完全消失。
即使把 15 个错误全部修完，得到的也只是"Editor 平台版本的一份源码"，
播放器构建依旧拿不到 `Sirenix.Utilities` / `Sirenix.Serialization`。
人工标定 2,700 个类型的条件编译边界不具可行性。

> **最终建议**：把编译验证的成果定位为
> ① 证明反编译产物质量高度可信（99% 可编译）；
> ② 为逐模块阅读源码提供可编译的 IDE 环境；
> 生产使用仍然走 §2 的 DLL 保真包。

## 5. 风险清单（按严重度排序）

### 🔴 P0 · 阻断级

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| 1 | **`.meta` GUID 漂移** | `OdinPathLookup.asset` 以 GUID 硬绑定 `Sirenix.OdinInspector.Editor.dll`（`a4865f1a…`）。GUID 一变，Odin 直接无法初始化 | 包内 `.meta` **逐字节保留**，禁止 Unity 重新生成；构建后做 `diff` 校验（已实现） |

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| 5 | **Visual Designer 保存路径失效** | `OdinVisualDesignerConfig.DEFAULT_SAVE_PATH` 硬编码 `Assets/Plugins/Sirenix/…/Visual Designer/Saved`，**不走 GUID 回退** | 用户在该配置面板手动改保存路径 |

### 🟡 P2 · 需留意

| # | 风险 | 说明 |
|---|---|---|
| 9 | Unity 版本绑定 | 反编译依据 Unity 2021.3.45f2c1。`Sirenix.Reflection.Editor` 依赖 Unity internal API，**跨 Unity 版本极易失效**（internal 签名变动） |
| 10 | 授权合规 | Odin 是 Sirenix 商业付费资产。重打包**仅供已购许可证用户本机使用，不可再分发** |
